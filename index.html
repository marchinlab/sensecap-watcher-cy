v1.6.3
起点：公开上架时设备上跑的版本
2026-11-02
背景
它本身也是一次事故的产物：上一版把"什么时候去拉消息"写成了黑名单（不在这些状态就都拉），开机早期 Unknown/Starting 被放行，lwip 还没就绪就去建 HTTP 连接，断言失败，设备 2.5 秒一次无限重启。
改法
改回白名单（空闲 + 聆听），并保留上版的设计意图：收到消息先把 CPU 和背光从省电档拉回来，轮询周期 6 秒 → 5 秒。
结果
串口实测：拿到消息到起播 0.4 秒，设备待机时也会自动亮屏开口，不需要喊唤醒词。
教训：涉及网络调用的状态判断必须用白名单。黑名单永远会漏掉某个你还不知道的状态。

v1.7.1
三件"看起来像坏了"的事bugfix
11-04
① 不换图
待机永远停在同一张。计数器 pet_idle_ms_ = 0 写在了 idle 判定之前，每 33ms 先清零再累加，永远到不了 5000ms 的换图阈值。改成只在"确实离开待机"时清零。
② 闪旧眼
每次开机先闪一下旧形象。资源加载有约 5 秒空窗，原实现拿胶囊眼顶着。改成空窗期压住表情层，资源一就绪立刻换鱼；重试从 5 秒一次改 1 秒一次，连续 8 次失败才兜底回落（防止真黑屏）。
③ 假动画
GIF 根本没在动。2 帧版本的帧间差异平均只有 0.13，人眼不可辨。重做成 6 帧 / 150ms：角色浮动 ±6px + 左右摆 ±4px（错相），裙摆头发按高度剪切飘动，背景完全静止。
踩坑
GIF 每帧都是全量帧，8 帧全画面动要 9~15MB，直接写爆 14MB 分区。背景必须不动，只有角色带变化，压缩率才扛得住（264KB/张）。
v1.7.2
从整体浮动，到部件级动画新功能
11-04
反馈
整体浮动"人眼看起来有卡顿"，要的是人物眼睛和手在动，不是整幅图一上一下。
改法
背景与身体完全静止，只有两个部件动：
· 眨眼：每张底图用图生图生成"闭眼微笑"变体（17 张，高保真模式），模板匹配对齐眼位 → 把闭眼版的眼周椭圆羽化贴回 = 闭眼帧。14 帧 / 90ms，约 1.26 秒眨一次
· 手摆：8 张有独立手臂的，以腕部为轴把手部圆圈旋转 ±10°（正弦全程摆）；手贴脸或持物的 10 张不做，摆了会穿帮
结果
体积反而从 4.7MB 降到 3.4MB——变化区域从"整个角色带"缩到"眼 + 手"，压缩得更狠。
废案
最初试过"纵向压缩眼区"做眨眼，出来是糊掉的脸色块——压缩加边缘拉伸根本不像闭眼。

黑斑、眼罩，与标定错位bugfix

根因

v1.7.4
模型"答应了但不干活"架构性修复
11-04 13:05
现象
对它说"放首歌"，它嘴上答应，屏幕回 standby，一声没出。
根因
1. 设备端大模型收到"请调用播放工具"的指令后不执行——口头答应就走人；语音通道没有直推工具的能力，服务端没法替它调
2. 更隐蔽的一个：曲库音频全是立体声，而设备解码器只认单声道 Ogg Opus。TTS 恰好是单声道，所以新闻一直能播，只有音乐不出声
改法
1. 固件新增串口命令 lmusic play <url> / lmusic stop，直接调播放器；服务端匹配到歌就走串口直发，不再指望模型自觉
2. 转码管线补 -ac 1，存量 120 首原位重转单声道
验证
串口下发 → 设备 idle → notifying → 拉流 40 秒以上无断 → 停止命令正常。
方法论：能用串口直发的，就不要依赖模型的自觉性。这套做法后来直接撑起了整套网络电台。
v1.7.5
按了，停不住交互修复
11-04 14:48
现象
电台在播时按旋钮停不了；播放中喊唤醒词也听不到（这条其实是正常的——单通道，播报时麦克风不喂唤醒词，得先按停或等它说完）。
根因
两条路叠在一起：
· 旋钮老逻辑是"停播 + 顺手开会话"，看起来像没停
· 服务端已经串口下发成功，设备端模型又补发了一次播放请求，同一地址排进队列，在播放态每 300ms 重试、能等 12 秒。你按停、设备刚回空闲，队列里那条请求立刻又把它拉起来
改法
1. 单击时若播放器还在播 / 还在排队，直接停止并返回，不再开会话
2. 停止时连活动地址与播放标志一起清，堵住"停了 300ms 又响"
3. 播放请求加同一 URL 去重
4. 起播前二次校验队列没被清掉（防竞态）
5. 新增串口命令 state：打印设备状态 / 唤醒词运行位 / 语音处理运行位
语义
按一下＝停（停在待机），要说话再按一下。
验证
串口日志实证：播报中按键出现 State: notifying → idle。

一个错标在脸上的圆圈参数调优
11-04 15:15
现象
某张表情（咖啡馆比 V）待机时"围裙有一个圈在转"；其他表情手摆幅度偏小。

第二日 · 七个版本，全是真机上的具体故障

下午 16:20 之后到第二天中午，问题从「好不好看」变成了「有没有真的出声、有没有真的翻页」。这一轮修的全是链路，不是界面。
v1.7.7
清掉一直挂在脸上的生成水印资产修复
11-04 16:14
现象
看 18 张表情大图时才发现，右下角一直挂着「AI 生成」的水印——从 v1.7.2 起就在表上，只是小屏看不清。
根因
v1.7.2 重做部件动画时换了套生成脚本，直接用了原始底图，而旧打包链里的去水印步骤只跑过一次，没有跟过去。
改法
水印区收紧 + 取正上方地面块覆盖 + 12px 羽化融合（硬贴会复制出一排咖啡杯、横向色带）。关键是把去水印做成 load_base() 统一入口：底图和闭眼变体必须同源处理，否则差异法会把水印当成「眨眼差异」贴回来。
教训：资产管线换了入口，旧链的清洗步骤不会自己跟过去；差异法对「两边不一致」零容忍。
v1.7.9
换 WiFi 时别把形象弄丢 + 文字回到屏幕中间状态机 / UI
11-04 21:28
现象
出门切到新 WiFi，动图偶发解码失败一次，旧形象就被永久拆掉，退回一对胶囊眼，直到重启才恢复。
改法
解码失败只退后台重试（每秒一次，8 秒后转 30 秒慢速重试），不拆对象、不清注入函数；同时把「不再露出胶囊眼」写进可见性判断，内存恢复后自动把形象拉回来。
顺带
对话与播报文字改为黑字 + 透明底，浮在待机画面之上并居中排布，长文自动换行占屏，不再压在底部一条实心色带上。
教训：一次偶发失败不应该改变长期状态。「失败就降级」要带恢复路径，否则就是单向门。
v1.7.10
新闻优先，以及字幕时间轴贯通架构性修复
11-04 22:13
现象
21:00 晚间新闻没播——当时设备正在放音乐，播放态下压根不去取收件箱。
改法
播报态也取件，取到语音先停当前播放再起播；播放器只认空闲态，所以「先停再播」是必须的。另一条线把字幕打通：服务端逐段合成时用 Ogg granule 量出精确时长，拼成单条音频并附 subtitles[{start_ms,text}]，收件箱、云端镜像、预约队列、设备端全程透传。
细节
有字幕时不再弹整版标题清单卡，避免和滚动字幕叠屏。
教训：「取到了」不等于「播出了」。游标一旦前移，失败的消息就永久丢了——取件与起播之间必须有确认。
v1.7.12
字幕停在第一页：给播放器加一口墙钟进度兜底
11-05 09:51
现象
早报字幕只显示第一页，后面十几页不动。
排查
先把链路逐段证伪：收件箱 12 条字幕、时间轴 0→1171s 全对；音频是单流 Ogg（OpusHead 只有一个），时长与字幕吻合。固件里「解码进度 → 字幕索引」代码也通。剩下的唯一可能是进度回调实际没喂上来或恒为 0。
改法
起播后每秒一次 TickProgress：真进度还在往前走就不干预，一旦落后真实时长 1.5 秒以上，直接用起播以来的秒数推进字幕；真进度恢复后自动切回。两条路径共用同一个翻页函数，Stop 必须在锁外停定时器（回调要抢同一把锁，锁内停会死锁）。
日志
起播打字幕条数与首末时间点，每次翻页打文本，切换到兜底时打一条 WARN——下次复现一眼能分辨是「没触发」还是「进度卡住」。
教训：外部回调不可信时，要有一条自己能算的时钟兜底；兜底必须可退出，不能永久接管。
v1.7.13
标题会翻、正文没出现：根因根本不在固件正文分页
11-05 10:04
现象
v1.7.12 上机后字幕会翻了，但翻的全是标题，正文一段都没出现。
根因
服务端字幕表存的字段是每条新闻的标题（seg.display），正文 seg.text 从来没进过字幕表。设备端再怎么修进度，也翻不出不存在的东西。
改法
服务端改成正文分页：按标点把每段正文切成约 45 字一页，页内起点按字数比例摊到该段音频时长；超过上限就自动加大每页字数重排。字幕上限服务端 160 → 200（固件同步 60 → 200），长新闻可到 100+ 页。
实测
413 秒 / 40 页那条：设备报 subtitles=40，每约 10 秒翻一页；中途一次 2.3 秒不报进度，由墙钟兜底补上后自动切回。另把新闻播报音量提高 30%（限幅器压住峰值，实测不削波）。
教训：先确认「喂进去的数据对不对」，再修「显示逻辑」。横跨服务端与固件的链路，最容易在字段语义上错位。
v1.7.14
说句话就拍照，不用先按一下语音工具
11-05 11:33
做法
给设备加两个模型可见的工具：说「几多卡路里／呢碟嘢肥唔肥」触发拍照算热量，说「呢度系边度／认下呢个路牌」触发拍照认地点。取图 → POST 二进制 JPEG 到服务端 → 视觉模型识别 → 粤语结论 + 字幕 + 收件箱播报。
关键
工具描述里塞满粤语和普通话说法，否则模型会挑平台自带的「识别万物」——那条走平台音色、也没有正文分页字幕。地址不新增配置，直接复用收件箱的命名空间，改一处两边同步。
兜底
认不出食物时也播一句「睇唔清，影近啲、避开反光，再嗌我一次」，并把实情回给模型，避免它继续说「马上播报卡路里」。沉默比认错更糟。
教训：同一个能力挂两条入口时，得靠工具描述把意图分开；模型的「默认选项」未必是你要的那条。
v1.7.15
按旋钮停不了电台，以及被吞掉的那条早报占道根治
11-05 12:35 · 当前
现象
听电台时按旋钮没停成，电台一直占着播放通道；结果 12:00 那条早安被设备取走却没播出来，收件箱游标还前移了——消息静默丢失。
根因①
单击处理靠「状态记账」猜是不是在播：电台是长连接流，流断或状态回空闲但解码器还在出声时两处同时漏判，单击落到「开始对话」，根本没调 Stop。
根因②
起播函数返回 void，设备忙或播放器还占着时会静默 return；调用方不检查是否真起播，却已经清了队列、置了 playing_、推进了游标。
改法
① 直接读播放器的 active_：播报 / 音乐 / 电台 / 连播任一命中就无条件全停并吞掉这次单击，每次单击打四路状态日志。② 起播后校验「是不是真的起来了」，没起来就把稿放回待播队列继续重试，上限从 12 秒延到 36 秒；卡在播报态时主动让位。
结果
真机复测通过。判断有没有真播出，看云端的 playing / audioSeconds，别只看「消息被取走」。
教训：不要用「我以为它在播」的状态变量代替事实；单通道设备上，任何一次「清了队列却没出声」都是永久性丢消息。

常驻角色 · 它不再是「扮演」，而是「它自己」

给设备定了一个常驻身份：屏幕形象、说话口吻、播报声音三条线各自独立，又能一起出现在同一句回答里。

设定
人设文档按八块写全（身份、口吻、口头禅、边界、情绪、与用户的关系、禁忌、示例对话），再压成一段可粘贴的控制台版本。角色库新增常驻标记，状态加载时兜底回常驻；「退出扮演」只脱外壳、不脱底色。
关键
注入用的是「你就是……」而不是「请扮演……」。写成扮演，长会话里模型会把它当成一件可以随时脱掉的衣服，几轮之后就变回通用助手口吻。
声音分工
· 新闻 / 播报 → 云端 TTS：快、稳、段落时长精确，方便对齐字幕
· 角色传话 / 提醒 / 闲聊 → 本地自然粤语声线：定版声线由参考音频 + 方言标记 + 说话人嵌入确定，实测实时率约 2.7～2.8
· 实时对话 → 平台侧音色（控制台可换、可试听）
音量
新闻播报整体 +30%，转码后加限幅器压住峰值；实测平均电平 -17.0dB → -14.5dB、峰值 -1.3dB，不削波。电台里几个偏小的台单独 +50%，同样是「放大 + 限幅」两步，缺了限幅等于白放大。
小结：同一台设备上有三个嗓子是有意为之——速度、自然度、可控性三者不可兼得，按场景分派比强行统一更实用。

服务端之一 · 自建音乐平台

曲库从 3 首试听曲长到 120 首，这条线没有版本号，但每一步都是被一个具体故障推着走的。

第一轮
先把管子拓宽
起点
曲库只有 3 首试听曲，管理页上传上限 25MB，连一首 41MB 的无损都传不进去。
改法
· 上限 25MB → 300MB
· 前端原来把文件 base64 塞进 JSON（体积膨胀 1/3、大文件必超时），改成 XHR 直传二进制 + 实时进度条
· 服务端同步放宽请求体限制，鉴权兼容 query 参数与请求头两种方式
验证
41MB WAV 直传成功，转成 Ogg 后 915KB。
第二轮
批量灌库：3 首 → 120 首
改法
写了个批量脚本遍历本地音乐目录，从"歌手 - 歌名"前缀解析元数据，跳过已入库的；一批 Taylor Swift（8 首）+ 一批粤语（卫兰 / 容祖儿 / 李克勤 / 许美静 / 郑秀文许志安 / 粤语经典，109 首）。
结果
曲库 3 → 120 首，全部 24k 单声道 Ogg，合计 93MB。
第三轮
为什么"答应了却不播"
第一层
和 v1.7.4 是同一个事故的两个面：设备端模型收到"请调用播放工具"的指令后只口头答应，并不执行。服务端的解法是不再请求模型——匹配到歌之后，由服务端直接下发，把地址推给播放器。
第二层
改完发现 120 首一声不出，设备日志报 Only mono Ogg Opus streams are supported。转码管线少了单声道参数，而 TTS 恰好是单声道——所以新闻一直正常，只有音乐哑火。补参数，并把存量 120 首原位重转（120/0 全部成功）。
插曲
写脚本读 Ogg Opus 头判断声道数时读错了字节偏移（声道数在 magic+9，不是 +8 或 +10），第一版结论是"全是单声道"，白查一轮。
小结："能搜到、能匹配、能下发、能出声"是四段独立链路，任何一段断掉，用户看到的都是同一个现象——没声音。

服务端之二 · 网络电台

目标很朴素：让它当一台收音机，主要听香港、英国、美国的台，而且要真的能播——不接受"列表里有但点不动"。

选源
公开电台目录 + 一层实时转码
选源
用公开的电台目录接口按国家码 + 标签检索，按票数排序、过滤掉已失效的流。两个坑：接口要求带 User-Agent；本机走系统代理，而 Node 的原生 fetch 不读系统代理，境外请求必须显式挂代理，否则一律超时。
第一版崩点
设备端只吃单声道 Ogg Opus，而电台源是 MP3 / AAC / HLS 直播流——所以服务端做了一层实时转码代理，边转边推：
设备 GET /api/radio/stream?id=xx
   → 服务端 spawn ffmpeg 拉直播源
   → -fflags nobuffer -flags low_delay   # 低延迟，别攒缓冲
   → libopus 24k / 24kHz / 单声道
   → chunked 分块推给设备            # 边转边推，不是转完再给
细节
同一台被重复请求时复用同一个 ffmpeg 进程，避免多开把上行占满；请求断开就杀掉子进程。
落地
21 台：香港 6（港台 1/2/5 与普通话台在内）、英国 5（BBC World Service、Classic FM、LBC、Capital、Heart 80s）、美国音乐 4、美国新闻 6（MSNBC / CNN / Fox / NPR / NBC / Bloomberg）。
验证
"能不能播"浏览器里看不出来
真机计时
· RTHK 第一台：连续播 60 秒无断流，设备空闲内存稳定在 37–39KB
· 播放中直接换台：旧流停、新流起，不卡死
· 6 个美国新闻台逐个过：全部可播，CNN、Fox 起播偏慢（约 8 秒），30 秒窗口内稳定
坑①
不能用统一阈值判断"流是否健康"：HLS 源会预缓冲（14 秒拉到 40 秒的量），MP3 直播源是实时速率（14 秒就是 14 秒），同一套阈值必然误判其中一类。
坑②
换台必须先停：播放器只在空闲态接受新的播放请求，直接发新地址会一直排队到超时。所以每次切台都是"先停再播"，中间约 1 秒静音——单通道的必然代价。
坑③
本地 ffmpeg 直接拉境外源被网络策略挡住，改为统一走服务端转码端点验证。
收尾
接进语音，然后印成一张纸
工具
新增三个工具：开台 / 列台 / 停播。台名做了中英别名表（"BBC""国际台""古典台""福克斯""伦敦台""粤曲台"都能认），并且沿用最初那份 21 台清单的编号——说"第 16 台"必须真的是 MSNBC，编号重排过一次会让所有口令错位。
一个"故障"
播放中喊唤醒词没反应，不是坏了：播音时设备处于播报态，单通道下麦克风不喂唤醒词。要换台就"先按停，再喊唤醒词"。这条最后变成了一张桌面速查图，把 21 台和口令印在一起。

服务端之三 · 逐字字幕与准点播报

字幕不是「把文字塞进消息里」这么简单，它横跨合成、分页、预约、镜像、设备解码五段，任何一段没带上都会退化成「只有标题」。

时间轴
多段新闻用分段合成，每段时长由 Ogg granule 精确量出；整篇图文一次性合成的，先量总时长，再按字数比例摊到各页。正文按标点切约 45 字一页，页内起点按字数比例落在该段音频区间里。
三条路径
多段新闻、整篇图文、事件播报都必须带字幕；曾经只有第一条有，后两条上机就露馅。上限统一放到 200 条（服务端 160 页上限 + 设备端 200 条接收）。
推进
优先用解码进度；段边界偶发 2～3 秒不报进度，就用墙钟接管，真进度恢复自动切回。详见 v1.7.12 / v1.7.13。
准点
早报怎么做到 08:00 准时开口
链路
本机前夜预生成语音与字幕 → 写入云端预约队列（带释放时间）→ 云端每 10 秒扫描、到点释放进收件箱 → 设备每 5 秒轮询 → 亮屏开播。实测误差 ≤ 15 秒。
为什么
临时在 8 点整抓新闻 + 合成 3 分钟音频一定迟到；把重活提前到夜里做，早上只剩「释放」这个动作。
前夜 本机预生成（新闻抓取 → TTS → 字幕分页 → 单条 Ogg）
   → 预约队列 releaseAt=08:00
08:00 云端 10s 扫描释放 → 收件箱 seq+1
   → 设备 5s 轮询取件 → 起播 → 字幕跟进度翻页
部署纪律：重新部署前必须把云端收件箱拉回本机做一次同步，否则云端序号回退，设备会认为「这些我都听过了」，新消息静默丢失。另外旧预约不会因为改了字幕逻辑自动重做，要手动删掉当天预约再重新预生成。

服务端之四 · 拍照识别：热量、地点、语音指令

设备自带一个摄像头模块（SPI 取 JPEG，单张约 23KB）。这条线把「拍一张照」变成「说一句有用的话」。

食物
上传 JPEG → 视觉模型输出结构化结果（菜名、组成、估算克数、千卡、蛋白质 / 脂肪 / 碳水、置信度、备注）→ 自然粤语结论 + 字幕播报。另有手机取景页（拍照即出结果）、当日累计与本地留档。
地点
模型只准抄字和做客观描述，不准猜城市；把路牌、店招、地标文字交给本地规则库打分，再给区/街道级结论。把「识别」和「判定」拆开，是为了不让模型一本正经地编一个地名。
统一管道
enqueueSpeechItem()：一段文字 → 合成语音 → 正文分页字幕 → 收件箱。食物、地点、提醒、智能家居事件全部复用它，所以字幕与音量行为天然一致。
入口
Base64 JSON 一条、二进制 JPEG 直传一条（给设备）、手机取景页一条；语音指令那条挂在设备工具上（见 v1.7.14）。
兜底
认不出时也播「睇唔清，影近啲、避开反光，再嗌我一次」，并把实情回给模型——沉默比认错更糟。
踩坑：全局 JSON 解析器的 256KB 上限会在路由之前就把照片请求拒成 413，得给大请求体路径开白名单；另外预览图在内存里分配失败只影响屏幕回显，不影响上传，别误判成整个功能挂了。

服务端之五 · 智能家居（Home Assistant × 米家）全量能力

架构是四段：手表 ↔ 自建服务端 ↔ 本地网关（Home Assistant）↔ 智能家居云。自研设备想直接进厂商 App 需要企业资质，个人侧走不通，所以接的是官方云集成——账号授权后把已有设备同步进本地网关，再由手表用语音控制、用粤语听事件。

语音控制 手表 → AI 服务端（MCP 工具）→ 自建服务端 /api/mi/control
   → 本地网关 REST /api/services/<domain>/<service> → 设备
事件播报 设备状态变化 → 本地网关 → 轮询 / webhook → 粤语文案
   → 统一播报管道（语音 + 字幕）→ 收件箱 → 手表
A
语音控制：能说什么、能控什么
入口工具列设备控制查状态 三个工具挂进 AI 服务端；平台提示词里写死「涉及家电必须先调工具，不准凭空答好嘅」，并把家电与电台两类意图分开，避免互相误触发。
可控设备域灯 · 开关/插座 · 风扇 · 空调温控 · 窗帘/卷帘 · 扫地机 · 电视/盒子 · 加湿器 · 热水器 · 门锁 · 场景/脚本/自动化 · 数值/选择/布尔辅助实体 · 警报器 · 阀门 · 按钮 · 遥控器（共 19 类）。传感器域另计：数值、二值、设备追踪、事件。
动作全集开 / 关 / 切换（窗帘转开合、扫地机转启停回充、播放器转播放停止、按钮转按下、场景转触发）亮度 0–100% · 色温 2000–9000K · 颜色（10 色预设）设温度（空调 / 热水器 / 数值实体）空调模式（制冷 / 制热 / 抽湿 / 送风 / 自动）风速（百分比或高/中/低）窗帘位置% · 加湿湿度% · 播放器音量% · 播放 / 暂停 / 上一曲 / 下一曲。
不支持的组合返回粤语错误提示，不静默失败。
说法归一粤语 / 普通话 / 英文混说都收敛成标准动作：「熄灯」「较光啲」「开冷气」「较到 26 度」「制冷」「蓝色」「关所有灯」。模型偶尔把整句话塞进动作字段，也有兜底归一。
找设备别名表 → 实体 ID 精确/尾段 → 名称精确 → 双向包含 → 短名优先；多个命中给最多 4 个候选而不是乱选一个。支持「所有灯 / 全部插座 / 全屋」批量意图。
批量安全「关所有灯」会排除指示灯，不误熄摄像机、风扇面板上的状态灯。
查状态返回自然粤语摘要：开/关 + 亮度%、当前温度、设定温度、湿度%、百分比、电量% 与单位；不念实体 ID。
安全闸语音开锁默认禁用（可以上锁，不能开锁）；令牌、管理端点全部要鉴权；灯与开关的状态变化不进播报白名单。
B
事件播报：什么会响、什么不会吵
双通道本地网关状态每 5 秒轮询一次；另有 webhook 让网关自动化在状态变化瞬间主动推过来（更即时）。两条通道共用同一套文案与防抖，不会重复播。首轮只建基线，不补播开机前的旧状态。
会播的事件门铃烟雾 / 燃气报警漏水 / 水浸门窗打开人体 / 存在感应低电量门锁开 / 关事件实体防盗警报触发温度过高湿度过高——全部翻译成自然粤语短句，带优先级。
监听白名单只听二值传感器、门锁、事件、防盗面板、数值传感器；数值传感器里再只看电量 / 温度 / 湿度与关键词（门、窗、人体、烟、燃气、漏水、电量）。灯、开关、空调、风扇、窗帘、播放器、自动化的状态变化一律不播。
防吵规则同实体同类型 60 秒冷却、全局每分钟最多 3 条、按优先级从高到低播；恢复态与重复触发直接丢弃。
出口统一播报管道 → 收件箱 → 手表，可选用快声线（事件类求快）或本地角色声线（求口吻一致）。
C
网关侧基础设施与运维
集成官方开源云集成（厂商 2024-12 放出）：OAuth 账号授权 → 选家庭 → 按房间映射 → 过滤设备 → 生成条目。完成后本地实体从 17 个涨到 170 个 / 11 台设备。
令牌访问令牌 401 时用刷新令牌自动续期，不需要反复手工生成长期令牌；也支持热更新令牌而不重启服务。
授权入口提供一个「永不过期」的授权地址：每次访问都检查或重建配置流程再跳转登录页，避免昨晚生成的链接第二天失效；配套的桌面双击入口用独立浏览器配置绕开回调域名的本机解析问题。
管理端点状态设备列表控制令牌热更新事件 webhook播报自测授权跳转 —— 全部走同一个服务端进程，不另起服务。
自启本地网关开机自启且隐藏窗口；已在跑就跳过，避免重复实例抢端口。
D
当前状态与边界
已接通集成条目 loaded、170 实体（可控 94 / 传感器 48）、桥接 enabled / connected / polling 全为 true，9 个常用别名干跑全部命中；服务端与本地网关健康检查通过。
待实测真实门铃 / 传感器触发播报、语音真实改动设备状态尚未做端到端实测（链路已就绪）；另有 4 台设备当前离线，显示为不可用，对它们下控制会失败。
可扩展蓝牙传感器（人体存在、门磁等）可另用一块 ESP32 做蓝牙代理转发给本地网关，用设备密钥解密后生成二值传感器——正好落在事件白名单里，接好就能播「有人返嚟」。与官方云集成互补：一个管低功耗蓝牙传感器，一个管 WiFi / 云端设备。手表本身保持原固件，不刷成代理。
不做的事不把自研设备伪装成厂商设备（需企业资质）；不开放语音开锁 / 撤防；不让灯的状态变化刷屏。
小结：这层桥接的价值不是「多一个控制入口」，而是把家电状态变成可听的事件——手表不用一直盯着屏幕，也不用额外装一个 App。

版本纪律

每一版都走同一套流程，不允许跳步：

  1. 改版本头：版本号 / 日期 / 说明三段一起改，说明里写清"改了什么、为什么"。
  2. 编译：ESP-IDF v6.0，自定义唤醒词与阈值作为编译参数固定下来。
  3. 校验产物版本串：在 bin 里 grep 版本号确认等于版本头——出现过"编译发生在改版本号之前"，备份下来的镜像其实是上一版。
  4. 备份五件套：bootloader / 分区表 / ota_data / 应用镜像 / 资源镜像，按版本号归档。
  5. 写台账：追加一条记录，含根因与验证方式。
  6. 双分区烧写：运行分区与备用分区写同一份镜像。只写一个的话，一旦回滚就启动另一分区的旧固件，表现为"烧了新版但版本号还是旧的"。
  7. 云端与本机同版本：服务端逻辑改了要同步部署；部署前先把云端收件箱序号拉回本机对齐，旧预约队列里的稿件要手动重做，否则新逻辑只在新稿上生效。
判断设备当前版本不要看开机日志里的编译时间（构建系统不刷新那行），看开机打印的 FW vX.Y.Z，或串口敲 version。

沉淀下来的几条

状态判断用白名单

黑名单必然漏掉你还不知道的状态。那条 2.5 秒无限重启就是这么来的。

别指望模型自觉

模型会答应，但不一定调工具。能走串口直发的，就走串口。

解码能力是硬约束

设备只认单声道 Ogg Opus，音频管线必须按它转码，不是反过来。

动画做部件级

背景静止、只有眼和手动，既自然又能把体积压下来。

参数要看图验证

坐标标错半格、圆圈压到衣服，只有把帧放大拼一起逐帧比才看得出来。

每版都能回滚

五件套 + 台账，任何一版出问题都能几分钟退回上一版。

先查数据，再查显示

字幕翻的其实是标题——设备端再怎么修进度，也翻不出服务端根本没放进去的正文。

别拿状态记账当事实

「我以为它在播」不等于播放器真的在出声。读真实状态，起播后要确认，失败要把稿放回去。

外部回调要有自己的钟

进度回调会卡、会丢；墙钟兜底能让长播报一直翻页，但必须能自动退出。

认不出也要出声

沉默、静默失败、游标前移，是用户最没法自救的三种结果。宁可说一句「影近啲」。

事件要防抖，播报要排队

传感器会连发、会抖动；冷却 + 每分钟上限 + 优先级，才不会把提醒变成噪音。

部署前先对齐序号

云端序号回退，设备会把新消息当成听过的旧消息——一次部署就能让整天的播报静默消失。
